# RAG 构建问题与解决方案

本文按构建阶段记录**实际遇到**的问题、原因、处理方式和验证结果。后续出现新问题时，补充到相应阶段；尚未开展的阶段不预填假设性故障。记录中不复制教材正文、密钥或生成的全文索引。

## 1. 数据准备与来源校验

目前没有需要单独记录的故障。正式入库命令会核对本地 28 篇中英文教材 Markdown 的 SHA256；任一文件不符就停止构建。来源清单和下载约定见 [数据来源](数据来源.md)及[实施计划](图谱增强RAG实施计划.md)。

## 2. Markdown 解析与分片

本阶段的正式离线入库代码位于 [ingest.py](../src/kgrag/ingest.py)，测试位于 [test_ingest.py](../tests/test_ingest.py)。以下记录基于 2026-11-16 的本地运行。

### 2.1 代码注释被误判为标题（已解决）

- **现象**：直接用正则扫描以 `#` 开头的行时，Python 代码块中的注释被列为 H1 标题，导致小节边界错误。
- **原因**：简单扫描没有跟踪 Markdown 代码围栏的起止位置。
- **处理**：解析器先判断围栏状态，只在围栏外识别标题；围栏内的普通代码和注释继续保留。
- **验证**：自写测试断言代码注释不会产生小节；中文 Transformer 文档中的伪标题不再出现在片段的 `section` 字段。

### 2.2 正文前的执行代码和排版指令混入检索文本（已解决）

- **现象**：部分 D2L Markdown 在第一个标题前有构建用代码，正文附近还有章节锚点、图片宽度等排版指令。
- **原因**：按原始行直接分片会把这些非知识内容一起写入片段。
- **处理**：跳过第一个标题前的内容；将紧随标题的章节 `:label:` 保存为元数据；过滤独立的 `:label:`、`:width:`、`:height:` 指令。普通代码块和公式块仍作为整体保留。
- **验证**：自写样例检查章节锚点和代码块；实际语料构建完成后检查片段内容与小节字段。

### 2.3 D2L 代码构建标记残留（已解决）

- **现象**：第一次全量分片后，片段中仍出现 `#@tab`、`#@save` 等标记，其中 `#@save` 还可能写在有效代码行末。
- **原因**：只过滤整行指令时，行尾标记不会被清除。
- **处理**：删除独立的构建标记行；对行尾标记只删除标记部分，保留函数定义等有效代码。
- **验证**：先用自写样例复现失败，再修改解析器使断言通过；重新构建后检查生成片段，不再含上述两类标记。

### 2.4 长小节需要继续切分，同时保留出处（已解决，长度上限仍需完善）

- **现象**：只按 Markdown 标题切分会产生过长小节，也不方便把检索结果定位回原文。
- **处理**：先按段落、代码块和公式块划分；长段落在标点或空白附近切分并保留少量重叠；短块在同一小节内合并。每个片段保存语言、稳定 `chunk_id`、原始行号和固定 GitHub 提交的链接。
- **验证**：自写样例检查长段落、代码块完整性、重复运行的 ID 及出处链接；正式入库命令按列表项边界处理 28 篇教材和 2 篇自写示例后生成 555 个片段。
- **后续**：命令行默认的 `max_chars=1200` 是**字符数目标**，不是模型 token 上限。当前构建有 64 个完整代码块超过该目标。`build_corpus` 已支持传入实际模型的 token 计数器；选定 embedding 模型后仍需接入其 tokenizer，并确定超长代码块的处理规则。

### 2.5 Notebook 输出可能带入教材正文（已解决）

- **现象**：原学习 Notebook 在观察教材时保存了正文预览输出，若直接提交会把教材内容带入公开仓库。
- **处理**：此前提交 Notebook 时只暂存清除输出的版本；后来按项目需要删除了 Notebook，正式分片代码由 `ingest.py` 承担。教材文件和生成的 `data/index/chunks.jsonl` 仍被 Git 忽略。
- **验证**：此前提交的 Notebook 输出数为 0；删除后仓库不再包含该文件。发布前继续检查待提交文件，不纳入教材正文、生成索引或凭据。

### 2.6 重复文本生成相同片段 ID（已解决）

- **现象**：同一行内重复出现相同句子时，多个长段落子片段可能有相同正文与起始行号，首次运行正式入库测试时触发重复 `chunk_id` 错误。
- **原因**：片段 ID 仅使用来源、小节、起始行和规范化正文，无法区分同一行内的重复片段。
- **处理**：将小节内片段序号加入 ID 输入；序号只由该文档自身的分片结果决定，不依赖其他文档的导入顺序。
- **验证**：重复句子的自写测试先复现冲突，修改后断言 ID 唯一；新增本地文档后，旧文档片段 ID 和 URL 保持不变。

### 2.7 列表项被从中间切开（已解决）

- **现象**：连续的 Markdown 列表项被当作一个长段落，按字符预算切分后，后一片段可能从某个列表项的中间开始。
- **原因**：初版块解析器只把空行、代码围栏和公式作为边界，没有识别列表项标记。
- **处理**：把每个列表项先作为独立块，再在预算允许时合并相邻块；过长的单项仍按长段落规则处理。
- **验证**：用两条自写列表项先复现失败，再确认分片分别从 `- alpha` 和 `- beta` 开始。

## 3. 向量化与索引

已使用本地 BGE-M3 构建 555 个中英文片段的统一向量索引，并用中文问题验证可召回英文原文。当前没有需要单独记录的向量索引故障；模型版本和编码参数随索引保存，加载时会核对。相关实现见 [embed.py](../src/kgrag/embed.py)。

## 4. 召回与图扩展

图谱抽取与 49 条候选边的逐条审核详情见 [图谱抽取抽查](图谱抽取抽查.md)。以下只记录影响构建和检索路径的问题。

### 4.1 结构校验通过的图边仍可能没有语义依据（部分解决）

- **现象**：第二轮真实 API 抽取的 96 条候选边全部通过关系类型、置信度和证据 ID 的结构校验；但按类型抽查 40 条时，10 条应拒绝、1 条待定。后续检索又暴露 9 条以 `EncoderBlock`、`DecoderBlock` 或 `sequence_mask` 等代码符号为概念节点的活跃边。
- **原因**：结构校验只能确认边格式和证据片段存在，不能证明指定原文直接支持关系的类型、方向和概念范围。
- **处理**：把拒绝和待定记录写入 [graph_reviews.yaml](../config/graph_reviews.yaml)，重建时排除；收紧抽取提示词，并在开发问题检索结果中优先审核影响排序的边。
- **验证**：使用会在抽取缓存未命中时立即抛错的客户端离线重建，图中活跃边由 85 条降为 76 条；审核计数为 29 通过、19 拒绝、1 待定，0 条失效记录，没有新增付费抽取调用。
- **后续**：仍有 47 条活跃边未逐条审核。开发题阶段继续复核高影响路径，封存测试前冻结图；上述分层抽查的 29/40 不是全图精度估计。

### 4.2 同一英文概念的大小写差异切断两跳路径（已解决）

- **现象**：`Recurrent neural networks` 和 `recurrent neural networks` 在活跃图中成为两个节点，从前者出发无法走到后者连接的 `recurrent layers`。
- **原因**：图的普通概念标签保留原始大小写，原先只有已审核跨语言别名经过不区分大小写的归一。
- **处理**：对所有图边标签建立不区分大小写的节点映射；跨语言译名仍只依据已审核别名表合并。
- **验证**：新增回归测试先复现断路，再确认两跳路径、关系和逐跳证据 ID 均保留；本地图重新加载后可连通。

### 4.3 跨语言别名的字面校验不能代替语义复核（已复核现有六组）

- **现象**：别名校验可确认中英文标签分别出现在指定的不同语言片段，却不能单凭字面出现判定两者是同一概念。`attention` 等短词尤其需要上下文。
- **处理**：逐组对照现有六组别名的中英文指定片段；四组教材别名有术语括注或匹配的定义与上下文，两组自写示例有平行定义，因此本次均保留。别名只归一概念节点，不合并中英文证据片段 ID。
- **验证**：跨语言路径和原文片段 ID 分别检查；当前活跃边没有使用 `attention` 或 `query` 这两个较宽泛的短别名。逐组判断见 [图谱抽取抽查](图谱抽取抽查.md)。
- **后续**：这是助手复核，项目作者仍需独立审阅；新增别名继续要求指定双语原文证据。

## 5. 重排与上下文组装

三种模式 `dense`、`one_hop`、`typed_path` 已共用同一向量索引。下面的问题由三道本地探索性跨概念问题暴露；这些问题不属于封存测试集。

### 5.1 无关种子概念获得路径加分（已解决）

- **现象**：问“层规范化在 Transformer 编码器中起什么作用”时，首次运行的两跳模式把解码器代码类片段排到首位。
- **原因**：初版把向量种子片段上关联的任意概念都作为扩展起点，包括题目没有提及的概念；错误代码符号边又放大了噪声。
- **处理**：若题目提到的概念与种子概念有交集，只从这些概念扩展；把题目中空格分隔的 `Transformer 编码器` 与图节点 `Transformer编码器` 对齐，并排除上述代码符号边。
- **验证**：回归测试先复现无关路径加分；重新运行相同问题后，首项变为直接描述编码器层规范化的中文原文片段。

### 5.2 同一证据的路径选择忽略题目概念覆盖度（已解决）

- **现象**：同一原文片段有多条可达路径时，边置信度略高但偏离题目重点的路径会胜出。
- **原因**：初版只按路径分选择“最佳路径”，最终证据分数中的问题概念覆盖度没有参与路径选择。
- **处理**：用最终检索分数中的路径项与概念覆盖项共同选择该片段的最佳路径，并在结果中保留逐跳关系与证据 ID。
- **验证**：回归测试先显示偏题路径胜出，修复后选到同时覆盖两个题目概念的路径；本地教材问题的首项路径回到“Transformer编码器—层规范化”。

### 5.3 上下文预算与证据噪声仍需开发题验证（待完善）

- **现状**：三种模式都按同一 `--token-budget` 做片段去重、同文档章节限制和中英近重复限制；预算已计入答案生成实际使用的系统提示词、问题、证据正文和元数据。但当前中英混合计数器仍只是稳定近似，不是 DeepSeek 的实际 tokenizer，也未计入模型特定的消息开销。层规范化探索题的 Top-5 仍出现有原文依据、但偏离编码器问题重点的解码器证据。
- **验证**：测试覆盖相同预算、去重、一跳上限、无证据图边排除及路径权重消融；三道探索题中，中文问题能召回英文原文，束搜索题出现两跳英文路径。
- **后续**：在 12 道开发题上核查证据组并调参；正式对照评测前接入所选生成模型的 token 计数器，固定配置后再运行封存题。探索题结果不能作为正式效果结论。

## 6. 答案生成

已实现基于提供的原文片段生成中文答案，并校验回答中的引用 ID 和引用标记；无有效证据时拒答。当前没有需要单独记录的实际生成故障。真实 API 生成答案的三路对照与人工引用核查仍待开发题阶段开展。

## 新问题记录格式

在对应阶段新增三级标题，并依次写明：**现象、原因、处理、验证、状态或后续**。若问题尚未解决，写出可复现条件与当前阻碍；解决后更新原条目，避免同一问题分散在多处。
